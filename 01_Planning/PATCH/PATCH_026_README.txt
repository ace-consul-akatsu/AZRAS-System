PATCH_026 — 260918 UTC — v1.0.630
========================================

対象ファイル:
  - services/project_export_paths.py（_data_root_from_path のバグ修正）
  - dev_checks/json_save_folder_regression_self_check.py（新規、再発防止）

報告内容:
  マルコ氏より、Module 0の「Project JSON・CSV保存先を選択」で保存先フォルダー
  として実際に「JSON」という名前のフォルダー（例：
  Dropbox\015_AZRAS\AZRAS_v2.2.0\JSON）を選択しても、新規Projectの初回保存時
  にそのフォルダーの中ではなく、1つ上の階層（AZRAS_v2.2.0直下）にProjectの
  フォルダーが作成されてしまう、というバグ報告があった。添付スクリーンショット
  では、既存の2案件（260918_2×6_Sample、260918_AZRAS_Sample）はJSONフォルダー
  内に正しく格納されている一方、新規に作成した「260918_RC_Rahmen_Sample」だけ
  がJSONフォルダーの外（AZRAS_v2.2.0直下）に作成されていた。

原因:
  services/project_export_paths.py の _data_root_from_path() に、
  「フォルダー名が大文字小文字を無視して"json"と一致する場合は、その親
  フォルダーをデータルートとみなす」という特別処理が入っていた。これは
  本来、ポータブル版EXEの既定フォルダー構成 `EXE/Data/JSON` において、
  "Data"フォルダーが見つからない場合の保険的な処理として書かれたもの
  だったが、"Data"フォルダーの探索自体は別途、親フォルダーを遡る
  ループで既に行われており、この特別処理は実質的にそのケースでは
  発火しない（"Data"が先に見つかるため）。

  一方、ユーザーが独自に用意した保存先フォルダーがたまたま「JSON」という
  名前で、かつその上位に「Data」という名前のフォルダーが存在しない場合
  （まさに今回の報告のケース）、この特別処理だけが発火し、ユーザーが
  明示的に選んだフォルダーではなく、その1つ上の階層をProjectフォルダーの
  格納先にしてしまっていた。

  既存の2案件が正しく格納されていたのは、それらが既に
  `JSON/<Project名>/<Project名>.json` という形で自分自身のフォルダーを
  持っており、再保存時は「親フォルダー名 == Project名」という別の判定
  （現状維持）が先に一致していたため。バグが発火するのは、Project名の
  フォルダーがまだ存在しない「新規Project初回保存」の瞬間だけだった。

対応:
  _data_root_from_path() から、フォルダー名が"json"と一致する場合の特別
  処理を削除した。"Data"祖先フォルダーの探索ロジックはそのまま維持して
  いるため、ポータブル版EXEの `EXE/Data/JSON` 構成には影響しない。これに
  より、ユーザーが明示的に選択したフォルダー（フォルダー名が偶然「JSON」
  であっても）がそのまま保存先として尊重されるようになった。

検証:
  以下3パターンを実際にコードで再現し、修正後にすべて期待通りになることを
  確認した。
    A. 新規Projectを、"Data"祖先を持たない独自の「JSON」フォルダーへ初回
       保存 → 修正前：1つ上の階層に作成されるバグを再現 → 修正後：選択した
       JSONフォルダーの直下に正しく作成される。
    B. ポータブル版EXEの `EXE/Data/JSON` 構成 → 修正前後ともに `Data`
       フォルダー直下に正しく作成される（回帰なし）。
    C. 既にJSONフォルダー内で自分自身のフォルダーを持つ既存Projectの
       再保存 → 修正前後ともに同じ場所に留まる（回帰なし）。

再発防止:
  dev_checks/json_save_folder_regression_self_check.py を追加し、上記
  A・B・Cの3パターンを自動検証する。
